# MeLawDy

Стартовый каркас сайта MeLawDy: статический web, один Python API на FastAPI, PostgreSQL с pgvector. Код поиска и ранжирования лежит в `ml/` и вызывается внутри API без отдельного сетевого сервиса.

## Запуск

Нужны Docker Engine и Docker Compose v2. После клонирования репозитория из корня проекта:

```sh
docker compose up --build
```

Для разработки без загрузки модели эмбеддингов в RAM:

```bash
EMBEDDINGS_ENABLED=false docker compose up --build -d
```

Или задайте `EMBEDDINGS_ENABLED=false` в `.env`. При сборке не устанавливаются PyTorch и SentenceTransformers, индексация эмбеддингов при старте пропускается, поиск использует BM25 и не загружает модель. Веса на диске сохраняются. Для включения модели задайте `EMBEDDINGS_ENABLED=true` и пересоберите API: `docker compose up --build -d api`.


`.env` для локального запуска необязателен. Чтобы изменить порты или учётные данные, скопируйте `.env.example` в `.env` и отредактируйте значения.
Если вы ранее запускали версию с отдельным `ml`-контейнером, один раз выполните `docker compose down --remove-orphans` перед новым запуском; данные в томах при этом сохранятся.

- Сайт: http://localhost:8080
- Панель администратора: http://localhost:8080/admin.html
- API и документация OpenAPI: http://localhost:8081/docs
- PostgreSQL: `localhost:5432`, база `melawdy`, пользователь `melawdy_app`

Nginx передаёт `/api/` в Python API. Все опубликованные порты привязаны к `127.0.0.1` хоста. Для доступа из интернета потребуется отдельная настройка домена, TLS и reverse proxy.

Nginx обновляет IP сервиса `api` через DNS с интервалом кэша 5 секунд. DNS-серверы берутся из `/etc/resolv.conf` контейнера при запуске; для Kubernetes имя API дополняется доменом текущего namespace из DNS search-списка. При необходимости hostname можно задать через `NGINX_API_HOST`. Пересоздание API-контейнера не требует перезапуска web. После обновления этого конфига пересоберите web: `docker compose up --build -d web`.

Развёртывание на VPS с доменом `lawmposer.ru`, HTTPS и отдельным namespace существующего k3s описано в [инструкции VPS](deploy/k3s/README.md). Локальный Compose работает независимо от него. Push в `main` автоматически обновляет VPS после успешных тестов GitHub Actions; текущий SHA сайта доступен в `https://lawmposer.ru/version.json`. Другие ветки публикуются после слияния в `main`.

## Запуск на Windows

Установите и запустите [Docker Desktop с WSL 2](https://docs.docker.com/desktop/features/wsl/), используя Linux containers. Dockerfile и `backend/entrypoint.sh` выполняются внутри Linux-контейнера; локальная установка Python или ручной запуск `.sh` через PowerShell не нужны.

Из корня проекта в PowerShell:

```powershell
docker info --format '{{.OSType}}'
docker compose up --build -d
docker compose ps -a
```

Первая команда должна вывести `linux`. После запуска откройте http://localhost:8080. Ключ `-d` запускает контейнеры в фоне; без него терминал остаётся занят выводом логов — это нормальная работа Compose.

`.gitattributes` закрепляет LF для shell-скриптов; Dockerfile дополнительно исправляет CRLF в `entrypoint.sh` при сборке, включая старые рабочие копии Windows. После получения этих изменений пересоберите API командой `docker compose up --build -d`.

Если сайт не открывается, сохраните вывод следующих команд:

```powershell
docker compose ps -a
docker compose logs --tail=100 api postgres web
```

Если проблема возникает при сборке, отдельно выполните `docker compose --progress plain build` и сохраните последние строки вывода. Ошибки скачивания образов или пакетов требуют проверки сети Docker Desktop; смена `entrypoint.sh` их не исправляет.

## Управление

```sh
# Остановить контейнеры, сохранив данные PostgreSQL и кэш модели
docker compose down

# Пересобрать и запустить в фоне
docker compose up --build -d

# Смотреть логи
docker compose logs -f
```

`docker compose down -v` дополнительно удаляет локальные данные PostgreSQL и кэш модели.

## Администратор и базовый интерфейс

Статический интерфейс использует HTML, CSS и JavaScript без frontend-фреймворков, сборки и внешних CDN. Главная страница загружает опубликованные материалы, Q&A и активные assessment-опросы из API; поиск использует локальный SentenceTransformer `alekseevpavel04/multilingual-e5-small-ru-law`. При каждом запуске API скрипт `ml.index_content` рассчитывает недостающие векторы чанков до старта сервера; подробности — в [настройке поиска](docs/search.md). В админ-панели доступны создание, редактирование и удаление статей, категорий, тегов, терминов, Q&A, опросов, вопросов, вариантов, результатов, правил, шаблонов и справочников пошлин.

Статьи открываются на `/article.html?id=<id>` через `GET /api/v1/public/articles/{id}`. Страница показывает категорию, описание, время чтения и текст из `content_item_chunks` в порядке `chunk_index`, а также ссылки на другие опубликованные материалы. Первый чанк выделен как вводный раздел; правила оформления текста описаны в [инструкции администратора](docs/admin.md#статья).

Вход (`/login.html`) и регистрация (`/register.html`) используют серверную cookie-сессию и CSRF. Демо-входа и восстановления прав из localStorage нет. После успешного входа или регистрации открывается личный кабинет: профиль, реальные счётчики, последние 25 своих документов и сохранённых расчётов. Управление контентом отображается только администраторам; сервер также проверяет их права. Зарегистрированные пользователи могут сохранять свои расчёты. Бекенд дополнительно содержит `/api/v1/cabinet` для документов, истории и избранного.

Калькулятор получает процедуры, классы МКТУ и доступность действующих ставок через `GET /api/v1/public/fees/catalog`, а сумму — через `POST /api/v1/public/fees/calculate`. Сервер выбирает единственную действующую ставку для точного сочетания процедуры, класса (или без класса) и срочности и умножает её на количество процедур, используя Decimal. Период ставки проверяется включительно по текущей дате UTC. При отсутствии ставки или пересечении периодов расчёт возвращает ошибку. Доплаты за другие классы, тип заявителя и льготы не рассчитываются: для них пока нет правил в бекенде. Справочники и юридические ставки заполняет администратор; демонстрационные суммы не используются. `POST /api/v1/public/fees/calculations` повторно вычисляет сумму на сервере и сохраняет расчёт текущему пользователю; требуется вход и CSRF.

Страница проверки музыки загружает активные шаблоны из БД. `GET /api/v1/public/capabilities` сообщает, что анализа аудио пока нет: загрузка отключена, фиктивные совпадения и проценты не показываются.

Для новой установки создайте первого администратора после запуска контейнеров:

```sh
docker compose exec api python -m backend.manage_admin --generate-password --credentials-file /tmp/melawdy-admin-credentials
docker compose cp api:/tmp/melawdy-admin-credentials .admin-credentials
chmod 600 .admin-credentials
docker compose exec api rm /tmp/melawdy-admin-credentials
```

Email по умолчанию — `admin@melawdy.local`. Сгенерированный пароль находится в `.admin-credentials`; файл исключён из Git и Docker-контекста. Для уже существующего администратора команда сохраняет прежний пароль. Если Python-окружение настроено локально и PostgreSQL доступен на `localhost:5432`, достаточно `python -m backend.manage_admin --generate-password`.

Альтернатива для автоматического создания: задайте `ADMIN_EMAIL`, `ADMIN_PASSWORD` (минимум 5 символов) и `ADMIN_FULL_NAME` в локальном `.env`, затем пересоздайте API. Пустой `ADMIN_PASSWORD` отключает автоматическое создание; существующий пароль не перезаписывается.

Порядок заполнения статей и assessment, команды смены пароля и описание доступа — в [инструкции администратора](docs/admin.md). Assessment пока можно редактировать и просматривать: прохождение с сохранением ответов и вычислением результата ещё не реализовано.

## Тесты

Тестируем поведение API, права доступа, расчёты, поиск и сохранность данных при сбоях. Не фиксируем число таблиц, текущий ID последней миграции, точный SQL и внутренние вызовы библиотек без необходимости.

Локально, из корня проекта:

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r backend/requirements.txt -r backend/requirements-test.txt
python -m pytest -q
```

Проверки клиентской сессии используют встроенный test runner Node.js 18+ без npm-зависимостей:

```sh
node --test web/tests/*.test.js
```

Регрессионная проверка Nginx при смене IP API выполняется отдельно с Docker: `python -m pytest -q backend/tests/infrastructure/test_nginx_dns.py`. Она создаёт временную сеть и контейнеры, проверяет GET и POST без перезапуска web и удаляет тестовые ресурсы; рабочая БД не используется.

Бекенд-тесты выполняются полностью в Python. Они проверяют схемы, функции API, репозиторий с mock-сессией, вход, права администратора, CSRF, сохранение материалов и расчёт пошлин; подключение к базе данных, Docker и запущенная PostgreSQL не нужны.

GitHub Actions запускает Python-тесты и проверки клиентской сессии на `push`, `pull_request`, `merge_group` и вручную. Отдельный CI job поднимает PostgreSQL с pgvector, применяет миграции, сверяет схему с моделями и проверяет связи, JSONB, деньги, поиск вектора и откат/повторное применение миграции. Он не входит в локальный запуск `python -m pytest`.

## Структура

```text
web/          интерфейс и Nginx reverse proxy
backend/      FastAPI, SQLAlchemy-модели, схемы запросов и доступ к БД
ml/           TF-IDF, локальные embeddings, индексация и поиск по контенту
migrations/   версионированные Alembic-миграции
deploy/       Dockerfile для PostgreSQL и заметки для деплоя
docs/         исходная ER-схема, принятые допущения и инструкции по поиску
```

`web/static/index.html` и `web/static/admin.html` используют обычные HTML-элементы и JavaScript без дополнительного frontend-фреймворка.

## Данные и миграции

Утверждённый стек: Python, FastAPI, SQLAlchemy 2, psycopg 3 и Alembic. В `backend/models/` представлены все 25 таблиц из [ER-схемы](docs/schema.mmd): пользователи, контент, опросы, пошлины, шаблоны, документы, история и избранное. Связи доступны как Python-объекты. Подробности типов, ограничений и предложенных enum-значений — в [описании базы](docs/database.md).

Новая миграция `0002_domain_schema` добавляет доменную схему. Старые UUID-таблицы `documents` и `document_chunks` сохраняются с данными; прежний `/api/v1/documents` продолжает работать с ними. Перенос в `user_documents` не выполняется автоматически: у старых записей нет владельца, типа документа и остальных обязательных полей новой схемы.

Миграция `0003_admin_sessions` добавляет серверные сессии администратора. Пароли хранятся как Argon2id-хеши, в базе сохраняется только хеш токена сессии. Операции изменения в админ-API и создание legacy-документа требуют действующую сессию администратора и CSRF-токен.

Цепочка миграций продолжается до `0007_e5_embeddings`: после схемы `main` она меняет размерность embeddings с 1024 на 384, очищает несовместимые векторы и пересоздаёт HNSW-индекс. Тексты и остальные данные сохраняются; embeddings нужно рассчитать заново. При ошибке `Can't locate revision` пересоберите API: `docker compose up --build -d api web`.

API выполняет `alembic upgrade head` при запуске. Это применяет недостающие миграции и к уже существующему тому PostgreSQL. Пример: `docker compose run --rm api alembic current` показывает текущую ревизию.

Для Python-окружения с доступом к PostgreSQL:

```sh
python -m alembic upgrade head
python -m alembic current
```

`content_item_chunks.embedding` хранит `vector(384)` для `alekseevpavel04/multilingual-e5-small-ru-law`, индекс HNSW использует cosine distance. TF-IDF выполняется через scikit-learn. Установка модели, предварительный расчёт embeddings и команды поиска описаны в [инструкции по поиску](docs/search.md). Docker устанавливает CPU PyTorch и sentence-transformers; юнит-тесты используют заглушку модели без скачивания весов.

`POST /api/v1/documents`, `GET /api/v1/documents` и `GET /api/v1/documents/{id}` — минимальный пример работы с записями. `POST /api/v1/analyze` пока явно сообщает, что ML-пайплайн не настроен. Загрузка файлов ещё не реализована.

Учётные данные в Compose предназначены только для локальной разработки. Перед публикацией задайте отдельные секреты, настройте TLS и резервное копирование данных.
